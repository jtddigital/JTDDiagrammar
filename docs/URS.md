## 1. Purpose
A multi-type diagram language. Users define diagrams (flowcharts, cross-functional flowcharts, state diagrams, more later) in structured text and render them to SVG through an API and a web app. An AI component (Claude) generates validated diagram source from documents and unstructured text. The first priority is the cross-functional flowchart (swimlanes × phases, Visio-style), but no part of the system other than its type plugin may assume it.

## 2. Conventions
- **ID**: `URS-<AREA>-<NNN>`. IDs are never reused or renumbered; retired items are marked `Withdrawn`.
- **Priority** (MoSCoW): M = Must, S = Should, C = Could, W = Won't (this release). W items keep their ID and stay `Proposed`; the matrix records why they were deferred.
- **Verify**: T = automated test, I = inspection, D = demonstration.
- **Status**: Proposed → Accepted → Partial (some acceptance criteria met; see matrix) → Implemented → Verified (automated test passes) — or Withdrawn.

### 2.1 Decisions
| ID | Decision | Consequence |
|----|----------|-------------|
| D-001 | **Internal hosting** (2026-11-11): the API and web app run on an internal network for trusted users. | No end-user authentication in this release. AI spend is still guarded by per-client rate limits and per-request token budgets (URS-AI-019, URS-AI-009). Public exposure would need auth first. |
| D-002 | **Canonical process metamodel** (2026-11-18): process-oriented types (lifecycle, sap and those to come) share one canonical metamodel, a named subset of UML (class, state machine and activity concepts, events, profiles). Platform concepts are UML profile stereotypes, never new metaclasses. | URS-PM-001..021. Authors keep writing in platform terms or the generic `process` type; UML is never exposed directly. Settled after a design review comparing a generic-first and a platform-first language (Copilot and Claude). |
| D-003 | **BPMN is a notation and an export, not the model** (2026-11-18): workflows are stored as UML activities, drawn in BPMN-style notation and exported one way as BPMN 2.0. | No round trip: BPMN edited in other tools is not read back (URS-PM-018). XMI export is out of scope. |
| D-004 | **Platform types first, generic type as fallback** (2026-11-18): depth comes from platform types (lifecycle, sap); a generic `process` type, written in the canonical terms with free stereotypes, covers platforms without one. | URS-PM-019, URS-PM-020. |
| D-006 | **Workspace in the browser** (2026-11-19): files, folders and every saved version live in the browser's own database (IndexedDB), on this computer only; the server stores nothing. Every save is kept forever. | A workspace belongs to one browser profile; `.zip` export is the backup and the way to move it. Storage sits behind one interface so a server or disk backend can be added later. URS-WS-001..007, WS-020. |
| D-007 | **Document engines built here** (2026-11-19): the Markdown parser and viewer, CSV parser, diff engine and `.zip` writer are written in this repo, with no third-party libraries (owner: such libraries come with trials or sign-ups). | Conformance is proven by the public CommonMark and GFM spec suites and by tests; more code of our own to maintain. URS-WS-012, WS-030, WS-040..042. |
| D-008 | **Diagram diff by element identity, side by side** (2026-11-19): two versions of a diagram are compared through their Graph IR by element id, drawn side by side with changes marked, plus a list of changes. No merged overlay drawing: laying out the union gives a third layout that matches neither version. | Works for every type without type-specific code (URS-WEB-010). URS-WS-035. |
| D-005 | **Shared library now, pipeline stage later** (2026-11-18): the process model is built as a shared library used by the existing types, which already share its concepts. A separate pipeline stage (platform source → process model → Graph IR) waits for a consumer other than drawing (a chart spanning platforms, BPMN export). | URS-PM-019 (library), URS-PM-021 (stage, deferred). |
